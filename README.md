# Java Debugger MCP для IntelliJ IDEA 2025.3

Плагин расширяет **встроенный MCP Server** IntelliJ IDEA инструментами Java-отладки.
Отдельный сервер или отдельный порт не нужен. Агент работает с сессией, видимой в окне Debug.

## Сборка

Нужны JDK 21 и установленная IDEA 2025.3 с включёнными Java и MCP Server.
В PowerShell:

```powershell
$env:JAVA_HOME = 'C:\path\to\jdk-21'
.\gradlew.bat buildPlugin
```

По умолчанию используется `C:/Program Files/JetBrains/IntelliJ IDEA 2025.3`.
Другой путь можно передать так:

```powershell
.\gradlew.bat buildPlugin '-PideaPath=D:/Apps/IntelliJ IDEA 2025.3'
```

Архив для установки: `build/distributions/idea-debugger-mcp-0.1.4.zip`.
Для отдельной тестовой IDE: `gradlew.bat runIde` (создаёт песочницу настроек).

### Как сделать zip-архив для плагина

Архив собирается стандартной Gradle-задачей `buildPlugin`. В PowerShell из корня проекта:

```powershell
$env:JAVA_HOME = 'C:\path\to\jdk-21'
.\gradlew.bat buildPlugin
```

Готовый архив появится в `build/distributions/` под именем `idea-debugger-mcp-<версия>.zip`
(версия берётся из `build.gradle.kts`). Этот zip — то, что нужно выбрать
в Settings → Plugins → шестерёнка → Install Plugin from Disk.

Если нужен чистый архив без кэша, сначала выполните `.\gradlew.bat clean`, затем `buildPlugin`.
Собранные zip-архивы в репозиторий не коммитятся — они пересобираются локально командой выше.

## Установка и подключение

1. В IDEA откройте Settings → Plugins → шестерёнка → Install Plugin from Disk.
2. Выберите ZIP из `build/distributions` и перезапустите IDE.
3. В Settings → Tools → MCP Server включите сервер.
4. Скопируйте конфигурацию подключения подходящего типа для вашего агента из этой страницы настроек.
   Если встроенный MCP уже подключён, адрес менять не нужно.
5. Перезапустите MCP-клиент. В списке инструментов должны появиться `jdebug_*`.
6. Откройте Java-проект с готовой конфигурацией запуска. Агент может запустить её через `jdebug_start`; кнопка **Debug** также работает.

## Инструменты

| Инструмент | Назначение |
| --- | --- |
| `jdebug_start` | Запуск существующей конфигурации в Debug по точному имени |
| `jdebug_sessions` | Список живых debug-сессий и их идентификаторов |
| `jdebug_status` | Состояние сессии и текущая позиция |
| `jdebug_consoles` | Список открытых консолей Run/Debug, включая завершённые процессы |
| `jdebug_logs` | Последние строки вывода приложения из выбранной консоли |
| `jdebug_log_cursor` | Фиксация конца консоли перед вызовом метода |
| `jdebug_logs_since` | Новые сообщения после курсора, с ожиданием текста или таймаутом |
| `jdebug_search_logs` | Поиск в IDE: только совпадения с контекстом или количество совпавших строк |
| `jdebug_control` | `resume`, `pause`, `stepOver`, `stepInto`, `stepOut`, `stop` |
| `jdebug_stack` | Стек активного приостановленного потока |
| `jdebug_variables` | Переменные указанного кадра |
| `jdebug_evaluate` | Java-выражение; при необходимости прямые поля/элементы результата |
| `jdebug_breakpoints` | Список Java line breakpoint'ов |
| `jdebug_breakpoint` | Установка или удаление breakpoint'а по файлу и строке |

`sessionId` можно опустить, только если жива ровно одна сессия. При нескольких проектах
передавайте стандартный аргумент встроенного сервера `projectPath`.
Номера строк — **с единицы**, `frameIndex` — **с нуля**.
Пути в `jdebug_breakpoint` — абсолютные или относительно корня проекта.

Пример последовательности вызовов (аргументы в JSON):

```text
jdebug_sessions    {}
jdebug_breakpoint  {"filePath":"src/main/java/example/Main.java","line":15}
jdebug_start       {"configurationName":"DebugDemo"}
jdebug_sessions    {}
jdebug_control     {"action":"resume","sessionId":"ID из списка"}
jdebug_status      {"sessionId":"ID из списка"}
jdebug_stack       {"sessionId":"ID из списка"}
jdebug_variables   {"sessionId":"ID из списка","frameIndex":0}
jdebug_evaluate    {"sessionId":"ID из списка","expression":"order.getTotal()","maxChildren":20}
```

После управления выполнением дождитесь `state: suspended` через `jdebug_status`.
`jdebug_start` возвращает `submitted: debug`: это подтверждение отправки запуска,
а не появления сессии. Дождитесь её через `jdebug_sessions`, затем проверяйте
`jdebug_status`. Не повторяйте запуск автоматически: сборка или подключение
отладчика могут занять время. Ошибки асинхронного запуска смотрите в IDEA.
Имя конфигурации должно быть точным и уникальным; список доступен через
`get_run_configurations`. Инструмент не перезапускает живую debug-сессию с тем же именем.
Команда шага возвращает подтверждение отправки, а не обещание завершения шага.
Если приложение закончило работу, сессия исчезает из `jdebug_sessions`.

## Чтение логов из IDE

### Поиск без выгрузки всей консоли

Начинайте с `jdebug_search_logs`: поиск выполняется в IDE на фоновом потоке по неизменяемому
снимку буфера. В контекст агента попадают только ограниченные фрагменты результата.

```text
jdebug_search_logs {"query":"Exception","summaryOnly":true}
jdebug_search_logs {"query":"order-123","maxMatches":5,"contextLines":2,"maxChars":3000}
jdebug_search_logs {"query":"ERROR","consoleId":"ID консоли","afterCursor":"КУРСОР"}
```

По умолчанию поиск без учёта регистра, до 20 фрагментов, по одной строке контекста с каждой
стороны и до 4000 символов текста суммарно. `ignoreCase: false` включает учёт регистра.
`query` — буквальная подстрока на одной строке, до 256 символов. Регулярные выражения не используются.
Результаты идут от новых к старым; каждый фрагмент содержит номер совпавшей строки, смещения
в снимке и признак `clipped`. Один фрагмент ограничен 2000 символами. Контекст соседних совпадений
может пересекаться. В режиме `summaryOnly` текст логов вообще не возвращается.

`matchingLines` — количество строк с совпадениями в просмотренном диапазоне, а не число
вхождений подстроки. По умолчанию просматривается последний миллион символов; параметр
`maxScanChars` позволяет задать от 1 до 5000000. `scanTruncated: true` означает, что более старый
текст не просмотрен: нулевой результат тогда не доказывает отсутствие совпадений во всей консоли.
`outputTruncated` означает, что часть найденных строк не вошла в лимиты ответа.
`afterCursor` ограничивает поиск новыми сообщениями; недействительный курсор возвращает ошибку.
Номера строк и смещения относятся к `snapshotStamp` и могут измениться при обновлении буфера.

### Последние строки

`jdebug_consoles` возвращает открытые вкладки Run/Debug с `consoleId`, именем и признаком
`readable`. Передайте выбранный `consoleId` в `jdebug_logs`:

```text
jdebug_consoles {}
jdebug_logs {"consoleId":"ID из списка консолей","maxLines":200,"maxChars":20000}
```

Для живой debug-сессии вместо `consoleId` можно передать `sessionId` из `jdebug_sessions`.
Если доступна ровно одна читаемая консоль, оба идентификатора можно опустить.
Чтение не требует остановки на breakpoint и работает для обычного запуска Run.
После завершения процесса используйте `consoleId`, пока вкладка остаётся открытой.

Ответ содержит `text`, `truncated`, `bufferChars`, `returnedChars` и `pendingOutput`.
Ограничения: `maxLines` от 1 до 2000, `maxChars` от 1 до 100000. При ограничении по символам
первая возвращённая строка может быть неполной. `truncated` показывает сокращение текущего буфера,
а не наличие всей истории запуска. Повторный вызов возвращает новый снимок последних строк.

Инструмент читает текстовую консоль приложения, включая stdout/stderr и сообщения логгера,
направленные в неё. Файл `idea.log`, отдельные вкладки файлов логов и нестандартные консоли
не поддерживаются. Очищенный или вытесненный кольцевым буфером текст восстановить нельзя.
После обновления установите новый ZIP через Install Plugin from Disk и перезапустите IDEA и агента.

### Новые логи после вызова метода

Перед вычислением выражения сохраните курсор. Затем прочитайте новые сообщения:

```text
jdebug_log_cursor {"sessionId":"ID debug-сессии"}
→ {"consoleId":"ID консоли","cursor":"КУРСОР"}
jdebug_evaluate {"sessionId":"ID debug-сессии","expression":"service.processOrder()"}
jdebug_logs_since {"consoleId":"ID консоли","cursor":"КУРСОР","waitMs":10000,"contains":"Order processed"}
```

`contains` — обычная подстрока с учётом регистра. Без неё инструмент ждёт любое новое сообщение.
`waitMs` от 0 до 30000, по умолчанию 0 (немедленное чтение). Ожидание уступает управление IDE.
При таймауте уже появившийся текст также возвращается. Проверяйте `matched`, `timedOut` и `reason`.
`matched` без `contains` означает наличие нового текста, с `contains` — наличие искомой подстроки.

Для следующих чтений используйте возвращённые `consoleId` и `cursor`, чтобы не получать повторов.
`maxChars` от 1 до 100000 (по умолчанию 20000) ограничивает ответ: при `truncated: true`
следующая порция остаётся доступной по новому курсору. `reason: limit` означает, что ожидание
закончилось по лимиту вывода, а не по таймауту. Поиск выполняется в текущей порции;
если ожидаемая подстрока разрезана между порциями, увеличьте `maxChars` и перечитайте с исходного курсора.

Очистка, редактирование, вытеснение текста из буфера, замена документа или повторный запуск
делают старый курсор недействительным. Вместо незаметной потери сообщений инструмент вернёт ошибку:
нужно зафиксировать новый курсор. Курсоры действуют в пределах работы плагина и выбранного запуска.
Поздние сообщения фоновых потоков тоже могут попасть в ответ: курсор выделяет период времени,
но не доказывает, что каждое сообщение вызвано именно исследуемым методом.

## Проверка на маленьком приложении

Готовые настройки подключения Codex находятся в [`examples/.codex/config.toml`](examples/.codex/config.toml).
Это конфигурация для установленной IDEA 2025.3 на Windows: встроенный stdio-мост подключается
к MCP-серверу IDE на порту `64342`. Плагин Java Debugger MCP должен быть установлен в IDE.

Откройте папку `examples` как проект в IDEA и как рабочую папку в Codex.
Codex читает проектный `.codex/config.toml` для доверенных проектов. Также этот блок можно
добавить в `%USERPROFILE%\.codex\config.toml` для глобального подключения.
Если сервер `intellij` уже настроен глобально, повторно добавлять его туда не нужно.
При другом расположении IDEA замените все пути в `command` и `args`; при другом порте измените
`IJ_MCP_SERVER_PORT`. Для другой версии IDE возьмите актуальную stdio-конфигурацию из её настроек MCP.
После изменения настроек перезапустите Codex.

### Qwen Code

Готовый пример: [`examples/.qwen/settings.json`](examples/.qwen/settings.json).
Qwen Code подключается напрямую к SSE-серверу IDEA 2025.3:

```json
{
  "mcpServers": {
    "intellij": {
      "url": "http://127.0.0.1:64342/sse",
      "timeout": 30000
    }
  }
}
```

1. Включите MCP Server в IDEA и установите Java Debugger MCP.
2. Откройте папку `examples` в IDEA, затем запустите `qwen` из этой же папки.
3. Выполните `/mcp` в Qwen Code и проверьте сервер `intellij` и инструменты `jdebug_*`.
4. Запустите `DebugDemo.main` в IDEA в режиме Debug и попросите Qwen исследовать переменные.

Для другого проекта скопируйте `.qwen/settings.json` в его корень. Для глобального подключения
добавьте объект `intellij` в `mcpServers` файла `%USERPROFILE%\.qwen\settings.json`, сохранив
остальные настройки. При другом порте IDEA измените URL. После изменения перезапустите Qwen Code.
При нескольких открытых проектах передавайте `projectPath` в вызовах инструментов.

Формат конфигурации: [официальная документация Qwen Code](https://qwenlm.github.io/qwen-code-docs/en/users/features/mcp/).

### Проверка отладки

Файл `examples/DebugDemo.java` можно скопировать в обычный Java-проект.
Поставьте breakpoint на строке `int total = price * quantity;` и запустите `main` в Debug.
Попросите агента получить стек и переменные: ожидаются `price = 120`, `quantity = 3`.
Вычислите `price * quantity` — ожидается `360`.
Выполните `stepOver`, дождитесь остановки и прочитайте `total` — ожидается `360`.
Проверьте удаление breakpoint'а и завершите приложение через `resume`.
Затем вызовите `jdebug_consoles` и `jdebug_logs` для оставшейся вкладки:
в тексте ожидается `Total: 360`.

## Ограничения первой версии

- `jdebug_start` запускает готовую конфигурацию; подключение JVM и сами конфигурации запуска настраиваются в IDE.
- Стек и переменные читаются из активного потока. Другой поток выбирается в окне Debug.
- Кадры перечитываются после каждого продолжения. При изменении suspend-контекста во время чтения возвращается ошибка.
- Представления значений берутся из отладчика IDE; большие значения могут быть сокращены.
  Дочерние значения ограничены параметрами вызова. Именованные группы перечисляются, но не раскрываются.
- Ожидание ответа от отладчика ограничено 10 секундами на операцию. Таймаут вычисления не отменяет уже исполняющийся Java-код.
- Вычисление выражений может вызывать методы и менять состояние приложения, как Evaluate Expression в IDE.
- Установка breakpoint'а ещё не означает привязку к исполняемому коду: это видно по значку в IDE.
- Совместимость ограничена веткой IDEA 253 (2025.3).

## Основание реализации

Регистрация инструментов через extension point `com.intellij.mcpServer.mcpToolset`:
https://github.com/JetBrains/intellij-community/blob/idea/253.28294.334/plugins/mcp-server/src/com/intellij/mcpserver/McpToolset.kt

Управление отладчиком через `XDebugSession`, чтение через `XStackFrame`, `XValue`, `XDebuggerEvaluator`.
Все обращения к UI API запускаются на EDT, ожидание асинхронных результатов не блокирует UI.
