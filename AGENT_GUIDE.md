# Работа с Java Debugger MCP

1. Используй `jdebug_sessions`, чтобы получить sessionId. Если список пуст, попроси пользователя
   запустить нужную конфигурацию в Debug. При нескольких сессиях уточни нужную, если назначение не очевидно.
2. Всегда передавай projectPath при работе с несколькими проектами и sessionId при нескольких сессиях.
3. Для breakpoint используй `jdebug_breakpoint`: строка с единицы, путь относительно корня проекта или абсолютный.
4. `jdebug_control` отправляет команду. После resume/шага проверяй `jdebug_status` с ограничением числа
   попыток; не считай отправку команды подтверждением остановки. Если программа ждёт внешнего запроса,
   сообщи пользователю, какое действие воспроизведёт проблему.
5. При `suspended` получи `jdebug_stack` и выбери frameIndex с нуля. Затем используй `jdebug_variables`
   и при необходимости `jdebug_evaluate`. Повторно получай стек после каждого шага или продолжения.
6. Стек относится к активному потоку; для переключения на другой поток попроси пользователя выбрать его в Debug.
7. Вычисления могут менять состояние JVM. Не вызывай методы с побочными эффектами без необходимости для
   поставленной задачи. После таймаута не повторяй такое выражение автоматически.
8. Не удаляй существовавшие до исследования breakpoint'ы. Запиши свои новые точки и убери их после работы.
9. Выводы подкрепляй наблюдаемыми значениями, файлом и строкой. Не считай выражение успешно вычисленным,
   если сессия изменилась или инструмент вернул ошибку.
10. Для вывода приложения используй `jdebug_consoles`, затем прежде всего `jdebug_search_logs`
    с выбранным consoleId и конкретной ошибкой, request ID или именем метода. Для обзора количества
    совпавших строк используй summaryOnly. Начинай с maxMatches=5, contextLines=1 и maxChars=3000.
    Проверяй scanTruncated: поиск может просмотреть только часть буфера. Для нового вывода ограничивай
    поиск через afterCursor. Если фрагментов недостаточно, используй `jdebug_logs` с выбранным consoleId.
    Для живой debug-сессии допустим sessionId. Остановка на breakpoint не требуется.
    Начинай с последних 200 строк; увеличивай лимит при необходимости. Учитывай `truncated` и
    `pendingOutput`: это снимок буфера IDE, а не полная история логов. После завершения процесса
    читай по consoleId, пока вкладка открыта. Не подменяй логи приложения файлом idea.log.
11. Для логов после метода сначала вызови `jdebug_log_cursor`, сохрани consoleId и cursor,
    затем выполни метод и вызови `jdebug_logs_since`. Для асинхронного результата задай waitMs
    и при необходимости contains. Проверяй matched/timedOut/truncated/reason; продолжай с возвращённого
    курсора, не повторяя вызов Java-метода. При инвалидированном курсоре сообщи о возможной потере
    логов и создай новый. Не приписывай весь вывод консоли одному методу без дополнительных доказательств.
